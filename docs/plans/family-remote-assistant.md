# 家庭远程助手 — 方案

> 状态：草案（待评审）
> 关联：`AGENTS.md` 待办区「records 入口」「Android 验证」；本文是形态 C（远程监护）的落地设计。

## 1. 定位

**全家共用一个虚拟药箱。**

一个「家庭组（Household）」共享同一份用药数据：子女在自己手机上给父母配药、查看父母今天吃没吃、漏服时远程提醒；同住家属可以代操作、代记录。

一句话卖点：*不是"我的提醒闹钟"，是"全家的药箱"。*

### 1.1 范围边界（先划掉，防止蔓延）

本期做**虚拟药箱**——药箱 = 一个家庭组的用药数据集合，物理上药可以放在不同地方。

明确不做：

- 智能药盒硬件接入（开箱检测谁取了药）——远期，且是另一个品类
- 医生 / 药师端、用药建议、相互作用查询（合规成本极高）
- 短信 / 电话提醒（需要语音通道与按次计费，远期付费项）
- 家庭组内的聊天

## 2. 角色与真实场景

| 角色 | 典型身份 | 核心动作 |
| --- | --- | --- |
| 配置者 / 管理员 | 不住家的子女 | 配药、改剂量、看数据、收告警 |
| 被监护者 | 父母 | 收提醒、点「已服用」 |
| 同住家属 | 配偶、护工 | 代操作、代记录 |

**关键设计认知：被监护者可以没有账号。**

`persons`（用药人档案）和 `household_members`（账号 ↔ 档案绑定）是两个概念。父母可以只作为「档案」被子女代管，自己不必装 App、不必注册。一旦父母不装 App，产品自动退化为「一台手机全家共用」形态——这条降级路径必须始终可用，否则远程助手对不上真实家庭。

## 3. 功能范围

### 本期

1. 家庭组：创建、邀请码加入、角色（owner / admin / member / viewer）、退出与撤销授权
2. 数据同步：多设备、离线优先、并发写合并
3. 远程提醒与告警：服务端定时判定 + 远程推送
4. 「今天吃了吗」看板：按成员、按时间点的实时状态
5. 代操作与操作人身份：谁点的、在哪台设备上点的
6. 远程配置：子女改时间 / 剂量，父母端生效并重排本地通知
7. 库存共享与补货提醒：现有 `LOW_STOCK_DAYS` 能力扩展到组内广播

### 本期之后的付费墙

多用药人上限、远程监护、历史导出、高级 Widget。免费版保留「单人完整闭环 + 一个家庭组只读」，否则没口碑也没转化。

## 4. 数据模型

### 4.1 新增表

```ts
households        // id, name, createdAt, createdBy
household_members // householdId, userId, personId(可空), role, joinedAt
devices           // id, userId, pushToken, platform, lastSeenAt
alerts            // id, householdId, type, personId, refId, createdAt, resolvedAt, deliveredTo[]
```

### 4.2 现有表的改动

| 表 | 改动 | 理由 |
| --- | --- | --- |
| `persons` | 加 `role`（self / spouse / parent / child / other） | 看板与通知文案要区分「爸爸」「妈妈」 |
| `persons` | 加 `updatedAt` / `deletedAt` | 合并策略需要 |
| `medications` | 加 `updatedAt` / `deletedAt` | 同上；库存天然共享，是并发写热点 |
| `plans` | 加 `updatedAt` / `deletedAt` | 同上；远程改配置的主战场 |
| `settings` | 从全局单行拆出 per-person 覆盖列 `personOverrides`（JSON） | 老人的免打扰时段和年轻人不同 |
| `usages` | 加 `recordedBy`（text，快照操作人姓名）、`source`（self / family / auto） | 代操作身份；遵守快照不可变硬规则，存姓名不存 userId 引用 |
| `reminders` | **不加同步字段** | 见 4.3 |

迁移落在 `src/db/client.ts` 的 `MIGRATION_V4`，`schema.ts` 与 `client.ts` 必须同步改（硬规则 26）。

### 4.3 哪些数据需要双向合并（本方案最重要的一个决定）

现在 `repo.ts` 是整份快照 `replaceAll`，多人并发写下后写会整份覆盖前者的改动。但不加区分地全表上合并是过度设计：

| 表 | 同步策略 | 原因 |
| --- | --- | --- |
| `persons` `medications` `plans` `settings` `household_members` | **字段级 LWW**（记录级 `updatedAt` + 软删除） | 真正需要合并的只有这五类 |
| `usages` | **append-only**，带 `clientId` 去重 | 服药记录只新增不修改，天然无冲突 |
| `reminders` | **不参与同步，本地派生** | 它由 `plans` 经 `syncReminders()` 纯函数算出，拉到新 plans 后本地重算即可 |

这一刀把"云端实时多人协作"降级成"五张表的 LWW + 一张追加日志 + 一张本地派生表"，实现量和出错面都小一个量级。

### 4.4 合并规则

- 同一条记录同字段并发写：取 `updatedAt` 晚的
- 不同字段并发写：按字段合（记录级 LWW 会丢一个，故用字段级）
- 删除 = 软删除（`deletedAt`），墓碑保留，避免"删了又复活"
- 合并前落一份本地快照备份，合并失败可回滚——数据丢失是这个功能最致命的失败模式

## 5. 服务端（最小集）

**选型：Supabase（Postgres + Auth + RLS + Realtime）+ Cron Trigger + Expo Push。**

排除项：CloudKit + CKShare（iOS 独有，Android 无对应物，本项目要双端）；自建服务器（没必要）。

### 5.1 为什么必须上服务端

远程推送要在**固定时间点**触发（准点、宽限期结束），iOS 不允许客户端代码在那个瞬间于后台发起网络请求。设备直连 Expo Push API 只能做到"父母打开 App 时才推"，不是"漏服即告警"。

### 5.2 告警规则引擎

复用 `store.ts` 里已有的常量作为单一来源：`GRACE_MINUTES`、`LOW_STOCK_DAYS`、`missedAlertStreak`。规则引擎不另造一套阈值。

| 规则 | 触发时机 | 推送对象 | 内容（脱敏） |
| --- | --- | --- | --- |
| 到点 | 计划时间 | 被监护人本人设备 | 「该吃药了」 |
| 宽限将过 | 计划时间 + 45min | 被监护人 + 同住家属 | 「还有 15 分钟」 |
| 漏服确认 | 计划时间 + `GRACE_MINUTES` | 管理员 | 「爸爸有一项待服药未处理」 |
| 连续漏服 | 达到 `missedAlertStreak` | 管理员 | 「爸爸连续 N 次漏服」 |
| 库存低 | 剩余天数 ≤ `LOW_STOCK_DAYS` | 管理员 | 「有药品快吃完了」 |
| 将过期 | `expiryDate` − 30d | 管理员 | 「有药品即将到期」 |

`alerts` 表负责去重：同一 `refId` 同一类型只推一次，`resolvedAt` 记录关闭时机。

### 5.3 推送内容脱敏（硬要求）

远程推送的 body **不带药名、不带剂量、不带剂量单位**，只带成员称呼与事项类型。细节一律点进 App 看。理由：推送内容会经过 Expo 的中转服务器，健康数据最小化。

## 6. 客户端改造点

遵循现有硬规则：屏幕永不直接碰 SQLite，持久化集中 `store.ts`，`useAppData()` 的调用方无感。

| 位置 | 改动 |
| --- | --- |
| `src/lib/household.ts`（新） | 家庭组 CRUD、邀请码、角色判断，保持纯函数形态 |
| `src/lib/sync.ts`（新） | pull → merge → 本地落库 → push；离线队列；合并前快照备份 |
| `src/lib/notifications.ts` | `rescheduleReminders` 只调度**本设备负责的用药人**的提醒；注册 / 刷新远程 push token |
| `src/lib/store.ts` | `AppData` 增加 household 上下文；`useAppData()` API 不变 |
| `src/db/schema.ts` / `client.ts` | 新表 + 新列 + `MIGRATION_V4` |
| `src/screens/home/` | 新增「家人今天的状态」区块（Expo UI 为主，遵守混排边界） |
| `src/app/(tabs)/profile/family.tsx`（新） | 家庭组管理：成员列表、邀请码、角色、撤销授权 |
| `src/screens/profile/persons.tsx` | 档案卡显示角色标识与「由谁管理」 |
| `src/i18n/dictionaries/{zh,en}.ts` | 新增 `family.*` 词条，两侧同步，`zh.ts` 不加 `: TranslationTree` |

## 7. 隐私与合规

健康数据属敏感个人信息，单独一节，不是附属说明。

1. **授权即明示**：邀请被接受时明确告知"你的服药记录将对家庭组成员可见"，并在设置中可随时撤销
2. **数据删除**：退出家庭组立即切断访问；`usages.personName` 是快照、按硬规则 22 不可改，因此退出时的处理是**软删成员 + 匿名化展示名**，聚合统计保留、姓名隐藏
3. **RLS**：Postgres 行级策略按 `householdId` 隔离，客户端不信任
4. **传输**：全程 TLS；静态加密由 Supabase 托管层负责
5. **最小必要**：只同步用药相关字段，不同步系统信息、位置
6. **境内合规**：面向 C 端需 ICP 备案与《个人信息保护法》下的单独同意流程

## 8. 里程碑

| 阶段 | 周期 | 内容 | 上后端 |
| --- | --- | --- | --- |
| M0 | 1–2 周 | 数据模型预埋（`persons.role`、`usages.recordedBy`、settings per-person 覆盖）、代操作入口、语音播报、配置二维码分享 | 否 |
| M1 | 2–3 周 | 家庭组 + Supabase + 同步。先做「配置下行」：子女配药 → 父母端生效，多设备读、单设备写 | 是 |
| M2 | 2 周 | 远程推送 + 告警规则引擎 + cron | 是 |
| M3 | 1–2 周 | 实时看板、代操作、撤销授权、匿名化、付费墙 | 是 |

M0 全部可在无后端情况下交付，且每单独交付都有用户价值。付费墙在 M1 之后立。

## 9. 风险与缓解

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 合并策略写错 | 数据丢失，最致命 | usages append-only + reminders 本地派生，把合并面压到五张表；合并前快照备份 |
| 父母不用智能机 | 远程助手价值打折 | 「一台手机全家共用」形态必须始终可用（M0 保障） |
| 邀请流程有摩擦 | 家庭组建不起来 | 邀请码一码到位，被监护人无账号也能被代管 |
| 授权焦虑 | 用户不敢开共享 | 默认只共享「今天的状态」，历史数据需二次确认 |
| 持续成本 | — | Supabase 免费额度 + Expo Push 免费额度，家庭规模远够 |

## 10. 验收标准

1. 子女手机改剂量 → 父母手机 60 秒内生效，本地通知已重排
2. 父母漏服 → 管理员手机 5 分钟内收到推送，点进 App 看到详情（药名只在 App 内出现）
3. 两端同时写不同字段 → 两个字段都保留，无一方被整份覆盖
4. 父母点「已服用」→ 子女手机看板实时更新，`usages.recordedBy` 记录为父母
5. 撤销某成员授权 → 该成员下次请求即失败，其历史数据对家庭组匿名化
6. 全程无后端时（飞行模式）→ 单设备完整闭环仍可用，恢复网络后合并成功
